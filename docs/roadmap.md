# 1단계 👤 Supabase Pro 전환

**왜:** 무료 500MB 는 약 3주면 찹니다. 차면 **수집이 실패하고 사이트가 멈춥니다.**
Pro 로 올리면 8GB + **매일 자동 백업** + '1주일 안 쓰면 정지' 규칙 해제.

> 5년 운영에서 진짜 위험은 용량이 아니라 **백업이 없는 것**입니다.
> 사고가 나서 몇 년치를 잃으면 돈으로 되살 수 없습니다.

**하는 법**

1. https://supabase.com/dashboard 접속
2. 우리 프로젝트 선택
3. 왼쪽 아래 **Settings** → **Billing**
4. **Upgrade to Pro** → 카드 등록

**확인:** 프로젝트 이름 옆에 `PRO` 표시가 뜹니다.

> 같은 프로젝트라 **데이터 이전도, 코드 수정도 없습니다.** 주소도 그대로입니다.

# 2단계 👤 `db/perf.sql` 실행

**왜:** 사이트가 데이터베이스에게 계산을 맡기게 하는 설정입니다.
안 하면 자료가 쌓일수록 화면이 느려지고, 서점별 화면의 날짜 목록이 60일에서 멈춥니다.

**하는 법**

1. Supabase → 왼쪽 **SQL Editor** → **New query**
2. 저장소의 [`db/perf.sql`](../db/perf.sql) **전체**를 복사해서 붙여넣기
3. **Run**

**확인:** `Success. No rows returned` 이 나오면 정상입니다.

**오류가 나면:** [`db/check.sql`](../db/check.sql) 을 같은 방법으로 실행하고,
나온 표를 저에게 그대로 보여주세요. 무엇이 없는지 한국어로 알려줍니다.

> ⚠️ 이 파일은 **여러 번 실행해도 안전**합니다. 데이터는 하나도 안 바뀝니다.

# 3단계 👤 `SUPABASE_ANON_KEY` 등록

**왜:** 지금 자동 검사에서 이 문구가 계속 뜹니다.

```
ℹ️ 화면 열어보기를 건너뜁니다.
```

**실제 데이터로 모든 화면을 열어보는 검사가 꺼져 있습니다.**
조회문 검사는 돌지만, "화면이 실제로 안 깨지고 뜨는가" 는 확인이 안 되고 있습니다.

**하는 법**

1. Supabase → **Settings** → **API Keys**
2. **anon / public** 열쇠를 복사
   > 🚨 **service_role 이 아닙니다.** anon(공개용) 쪽입니다.
   > service_role 은 모든 권한을 가진 열쇠라 절대 여기 넣으면 안 됩니다.
3. https://github.com/choimog/apple → **Settings**
   → **Secrets and variables** → **Actions**
4. **New repository secret**
   - Name: `SUPABASE_ANON_KEY`
   - Secret: 복사한 anon 열쇠

**확인:** 제가 검사를 한 번 돌려서 `✅ 모든 화면 정상` 이 나오는지 보고드립니다.

**왜: Pro 를 결제해도 이건 필요합니다.**


Pro 만으로는 **약 1년**이면 포함 용량이 찹니다. 초과분은 GB당 추가 요금이 붙습니다.
최근 90일만 Supabase 에 두고 나머지를 R2 로 옮기면 **2GB만 쓰게 되어 5년 내내 여유**입니다.

**데이터를 버리는 게 아니라 옮기는 것입니다.** 파일로 언제든 내려받을 수 있습니다.
R2 무료 10GB 에 5년치가 다 들어갑니다.

**하는 법:** [`docs/archive-setup.md`](archive-setup.md) 를 그대로 따라 하세요.

**확인:** 7단계에서 `옮길 날짜가 없습니다` 가 나오면 **정상**입니다.

# 7단계 🤖 로그인·권한

**왜 8번보다 먼저인가 — 2026-08-08 순서를 바꿨습니다**

처음에는 매칭 검토 화면을 먼저 만들려고 했습니다. 그런데 실제 보안 설정을
확인해 보니 **순서를 바꾸는 게 맞았습니다.**

지금 사이트는 **읽기 전용 열쇠**만 씁니다. 데이터베이스에서 쓰기 권한을
아예 회수해 두었습니다 (`db/rls.sql`).

```sql
REVOKE INSERT, UPDATE, DELETE, TRUNCATE
    ON ALL TABLES IN SCHEMA public
    FROM anon, authenticated;
```

검토 화면은 "이건 같은 책이다" 를 **저장**해야 하므로 쓰기가 필요합니다.
로그인 없이 쓰기를 열면 **주소를 아는 누구나 도서 묶기를 바꿀 수 있게**
됩니다. 관리자 열쇠를 사이트에 두는 것도 같은 이유로 안 됩니다.

다행히 데이터베이스는 처음부터 이걸 염두에 두고 만들어져 있습니다.
`book_matches` 표에 `decided_by`(누가 결정했나) 칸이 있고, `profiles` 표에
권한 칸이 있습니다. 로그인을 붙이면 **관리자만 쓰기** 규칙을 정확히 걸 수
있습니다.

**만들 것**

- 이메일 로그인 (Supabase 기능 사용)
- 관리자 / 보기 전용 권한 (`profiles` 표는 이미 있습니다)
- **관리자만** 매칭 결정을 쓸 수 있는 데이터베이스 규칙
- 특정 순위표만 외부에 공유하는 링크

# 8단계 🤖 매칭 검토 화면

**왜: 지금 가장 실질적인 구멍입니다.**

같은 책 묶기는 애매한 경우를 **'검토 필요' 로 표시만** 하고 넘어갑니다.
그런데 **사람이 그 결정을 내릴 화면이 없습니다.**
코드는 "사람이 내린 결정이 최우선" 이라고 되어 있는데, 정작 결정할 방법이 없습니다.

**잘못 묶인 책을 발견해도 대표님이 고칠 수가 없는 상태입니다.**

**만들 것**

- 검토가 필요한 짝을 모아 보는 화면
  (`book_matches` 에 `decision = 'auto_low'` 인 것들. 조회용 색인도 이미 있습니다)
- 두 책을 나란히 놓고 **[같은 책] / [다른 책]** 버튼
- 사람이 누른 결정은 **자동 로직이 절대 못 뒤집게** 저장
- 이미 내린 결정을 되돌리는 기능
